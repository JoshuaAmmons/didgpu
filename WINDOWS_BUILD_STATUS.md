# Windows GPU build — WORKING, no admin (#95)

## TL;DR

The Windows CUDA build **works end to end with no admin rights**. The
two-DLL split is implemented; it compiles, links, bundles, loads, and
**computes correctly on an RTX 4000 Ada (sm_89)**. `R CMD INSTALL` →
`library(didgpu)` → GPU estimators, verified **bit-exact** against the
pure-R reference (de Chaisemartin DID effects identical to R; saxpy
identical; fect SVD/demeaning within 1e-6).

## How it works: the two-DLL split

Windows can't link nvcc/MSVC objects into a MinGW DLL — they have
different C++ runtimes/ABIs, and MSVC objects reference symbols MinGW's
`ld` can't supply (`__security_cookie`, the mangled MSVC math overloads
`?sqrt@@YAMM@Z`, ...). So didgpu ships as **two DLLs** bridged by a
pure-C ABI (`inst/include/didgpu_cuda_api.h`):

- **`didgpu_cuda.dll`** — built by `nvcc --shared`, which drives MSVC's
  `link.exe`, so MSVC resolves all of its own C++ math/runtime symbols.
  Owns ALL CUDA state: device memory, cuBLAS/cuSOLVER handles, kernels.
  Exports the `extern "C" didgpu_cuda_*` functions via `didgpu_cuda.def`.
- **`didgpu.dll`** — the R-facing package DLL, built by Rtools MinGW g++
  exactly like a normal Rcpp package. Contains **zero** CUDA-runtime
  calls; links only against a MinGW import lib (`libdidgpu_cuda.dll.a`,
  generated by `dlltool` from the `.def`) and calls the C-ABI functions
  across the boundary.

**The key enabler (this session):** every `didgpu_cuda_*` entry point
takes HOST pointers and owns its device memory internally. Previously
four functions (`run_one_event_time`, `fect_fe`, `fect_svd_truncated`,
`fect_svd_softthreshold`) allocated device memory on the MinGW side and
passed *device* pointers across the boundary, which dragged `cudart`
into `didgpu.dll` and broke the MinGW link with undefined
`cudaMalloc`/`cudaMemcpy`/`cudaFree`. Moving that device management into
the `.cu` files fixed it (and is a clean improvement on Linux too,
where the single `.so` build stays bit-identical).

## The toolchain (no admin)

- **`tools/assemble-cuda-local.ps1`** downloads the CUDA 12.6.3 redist
  component ZIPs (nvcc, cudart, cccl, cuBLAS, cuSOLVER, cuRAND, **cuSPARSE,
  nvJitLink**) and merges them into `C:\Users\<you>\cuda_local` — a
  complete user-space toolkit. No installer, no UAC.
- **`tools/build-didgpu-win.ps1`** points the build at `cuda_local`
  (`CUDA_PATH`) and runs `R CMD INSTALL` with Rtools44 + VS Build Tools.
- A fast single-arch dev build: set
  `DIDGPU_CUDA_ARCH="-gencode=arch=compute_89,code=sm_89"` before the
  build (Makevars.win honours it; default covers Turing..Hopper).

## Runtime DLL bundling

`didgpu_cuda.dll`'s full load-time dependency closure ships in the
installed package's `libs/x64/` so the loader finds them alongside
`didgpu.dll` (R's `dyn.load` uses `LOAD_WITH_ALTERED_SEARCH_PATH`, so the
DLL's own directory is searched for its dependency tree):

```
didgpu_cuda.dll -> cudart64, cublas64, cusolver64
cusolver64      -> cusparse64, cublas64, cublasLt64
cublas64        -> cublasLt64
cusparse64      -> nvJitLink_120_0
```

Miss any one and `didgpu_cuda.dll` links fine but fails to LOAD with
"LoadLibrary failure: The specified module could not be found".
**cuSPARSE + nvJitLink** were the two that bit us — transitive deps of
cuSOLVER that weren't in the original redist set. (`curand64` is bundled
defensively, though the device-side cuRAND the kernels use needs no host
DLL — `didgpu_cuda.dll` does not import it.)

## Verified (sm_89, RTX 4000 Ada) — CUDA == R

Same results on Windows native and the Linux single-`.so` build:

| path                      | CUDA vs R         |
|---------------------------|-------------------|
| de Chaisemartin DID       | bit-exact         |
| saxpy                     | bit-exact         |
| truncated SVD (cuSOLVER)  | 6e-11 (recon)     |
| soft-threshold SVD        | 2e-8              |
| fect_fe two-way demeaning | 1e-6              |

## Remaining

  has no GPU/CUDA toolchain, so it can't build this variant; the realistic
